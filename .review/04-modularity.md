# v6.0 Modularity & Separation-of-Concerns Review

## Summary

The change set has a sound high-level intention—server-side quote/pricing and shared signup resolvers—but several boundaries are still porous. The most serious problems are the public UI reaching generated Convex internals, a module labelled as domain logic owning Next-to-Convex transport, and production Convex seeding depending on a test fixture. The signup and track-payment contracts are also re-described independently at the UI, Next route, Convex validator, and server projection layers, which makes the server-authoritative contract difficult to evolve safely.

No direct circular import was found in the reviewed paths. The larger risk is boundary inversion: domain modules import infrastructure, UI code imports generated backend details, and Convex mutations assemble presentation/email concerns.

## Layering map

```text
React components
  ├─ signup ───────────────> lib/convex/hooks/signup ───> lib/convex/api ───> Convex API
  │                         └─ lib/domain/signup/catalog (display normalization/types)
  └─ track-payment ────────> generated Convex api directly (TrackPaymentView)
                              └─ fetch Next route (editor contract duplicated in UI)

Next route
  ├─ signup submit ────────> lib/domain/signup/submission
  │                           └─ Convex transport + generated API (layer inversion)
  └─ track-payment edit ───> manual parser + lib/domain/track-payment/edit-token

Convex functions
  ├─ signupCatalog ────────> Convex validators + pure accommodation pricing
  ├─ finance ──────────────> a second event accommodation-context loader
  ├─ publicTracking ───────> shared signup loader + duplicated edit-choice projection
  ├─ signupSubmission ────> persistence + email URL/data orchestration
  └─ seedPreviewSimulation > lib/domain/legacy/preview-simulation
                              └─ tests/fixtures/legacy-preview.snapshot (test → production)

lib/domain
  ├─ finance/accommodation-amounts: genuinely pure and reusable
  ├─ signup/submission: imports Convex/Next transport (not pure domain)
  ├─ signup/submission-token and track-payment/edit-token: environment/HMAC infrastructure
  └─ legacy/preview-simulation: imports test fixture
```

## Findings

| ID | file:line | severity | coupling issue | proposed restructuring |
|---|---|---|---|---|
| MOD-01 | `components/track-payment/TrackPaymentView.tsx:6,19,77-87` | HIGH | The buyer-facing component imports `useQuery` from `convex/react` and `api` from `@/convex/_generated/api`, while the repository convention provides `lib/convex/hooks` as the client boundary. This couples presentation directly to generated function names and makes the component know that three separate Convex projections are required. | Add `lib/convex/hooks/track-payment.ts` with `useTrackPaymentView(bookingRef)` returning the three typed projections (or one server projection). The component should depend on that hook and a UI-facing DTO, not generated Convex internals. |
| MOD-02 | `lib/domain/signup/submission.ts:1-3,435-479` | HIGH | The module under `lib/domain/signup` imports `@/lib/convex/api`, `@/lib/convex/server`, and a Convex-generated `Id`, then performs the network mutation in `submitSignup`. Normalization/validation and transport are therefore inseparable, so this is not dependency-free domain logic and cannot be reused by a Convex runtime or pure tests without the Next transport. | Keep `normalizeEnvelope` and its pure validation error in `lib/domain/signup/submission-contract.ts`. Move `convexMutation(api.signupSubmission.submitSignupEnvelope, ...)` and result mapping to `lib/server/signup/submit.ts` (or a Convex hook/adapter), and have the Next route compose the two explicitly. |
| MOD-03 | `lib/types/signup.ts:1-112`; `app/api/signup/submit/route.ts:7`; `lib/domain/signup/submission.ts:128-360` | HIGH | `lib/types/signup.ts` is presented as a shared contract but is a runtime-dependent Convex module (`import { v } from "convex/values"`). Its validators are consumed by Convex files, while the Next route and domain submission path manually re-implement the same checks. The browser uses only TypeScript types; it does not reuse these validators. A Next API import of `signupSubmissionErrorCodeValues` also pulls a Convex-specific module into the server-side Next boundary. | Split pure types/literal constants into `lib/types/signup.ts` with no runtime imports. Put Convex adapters in `convex/validators/signup.ts`; put cross-runtime parsing/schema rules in a pure `lib/validation/signup.ts` (or a shared schema library), and make both the Next route and Convex boundary consume that contract. |
| MOD-04 | `lib/domain/legacy/preview-simulation.ts:16-23`; `convex/seedPreviewSimulation.ts:5-11` | HIGH | A production-deployed Convex mutation imports its seed data through a module in `lib/domain` that re-exports `tests/fixtures/legacy-preview.snapshot`. This is a test-to-production dependency and makes the production module graph depend on test paths and test-owned fixture semantics. | Move the sanitized deterministic fixture and its constants to `lib/legacy/preview-fixture.ts` (or `lib/fixtures/legacy-preview.ts`). Make tests import that production-safe fixture; keep `tests/fixtures` as a test adapter only, never an import target of `convex/`. |
| MOD-05 | `convex/signupSubmission.ts:1011-1059` | HIGH | The signup persistence mutation performs presentation/infrastructure orchestration: it loads event and Tikkie projections, reads `NEXT_PUBLIC_APP_URL`, builds buyer-facing URLs and placeholder room-assignment DTOs, then schedules an email. This makes the transaction-bound mutation depend on email template inputs, URL policy, and unrelated query APIs. Changes to email composition now require changing the persistence function. | Have the mutation persist the order and schedule an internal action with only `orderId` (or enqueue a mail job). Let a separate email orchestration action load the order/event/payment data, build URLs, and invoke the template adapter after the transaction. |
| MOD-06 | `convex/finance.ts:109-223`; `convex/signupCatalog.ts:412-536`; `convex/publicTracking.ts:391-482,629-630,992` | MEDIUM | `finance.ts` independently loads and assembles event config, rates, option definitions, and category/option maps even though `signupCatalog.ts` already owns the canonical public accommodation context. `publicTracking` correctly reuses `loadPublicSignupAccommodationContext`, but then independently rebuilds the edit-choice DTO (`buildEditChoices`) that the catalog projection also builds. These parallel projections can disagree about enabled options, categories, or config fields even when money is otherwise server-authoritative. | Extract a server-only `convex/accommodationCatalog.ts` with the context loader plus shared `buildPublicAccommodationChoices`/rate projection. Make `signupCatalog`, `publicTracking`, and the finance loader consume that one resolver; keep only endpoint-specific validators/DTO wrappers in each file. |
| MOD-07 | `app/api/track-payment/[bookingRef]/route.ts:26-70,200-303`; `convex/publicTracking.ts:340-383,754-775`; `components/track-payment/TrackPaymentAccommodationEditor.tsx:23-37,124-149` | MEDIUM | The edit envelope is described three times: a manual Next parser/authority-field list, Convex-specific validators, and a UI request/response type plus body builder. The same occupancy, night-before, option, idempotency, and ownership fields therefore have multiple normalization and acceptance points. The UI-facing `TrackPaymentEditContext` also manually mirrors the Convex return shape. | Define a pure `lib/domain/track-payment/edit-contract.ts` containing the envelope types, authority-field rejection, normalization, and request-body/response DTOs. Use a thin Next adapter and a thin Convex `v` validator adapter around it; expose a typed hook/transport function to the editor. |
| MOD-08 | `lib/domain/signup/submission-token.ts:40-58,223-237`; `lib/domain/track-payment/edit-token.ts:30-34,255-265,437-460` | MEDIUM | These modules are named and located as domain logic, but read process environment and perform HMAC/key-import infrastructure work. `buildTrackPaymentPermalink` also combines secret lookup, URL configuration, token minting, and presentation URL construction. That prevents the domain layer from being deterministic and makes runtime configuration an implicit dependency of supposedly shared code. | Split canonical envelope normalization/digesting into pure domain modules. Move secret lookup, Web Crypto HMAC, and app-URL/permalink construction to `lib/server/security` / `lib/server/track-payment`; inject the secret and base URL at the Next/Convex boundary. |
| MOD-09 | `convex/emailActions.ts:77-146,260-323`; `lib/email/templates/signup-confirmation.tsx:15`; `lib/email/templates/announcement.tsx:14` | MEDIUM | The Node action directly owns React-email rendering and separately hand-builds plain-text bodies, while the templates read `NEXT_PUBLIC_SITE_URL` at module load. HTML and text can drift, and the template package has a hidden Next-environment dependency when loaded by Convex. The action is consequently coupled to JSX, environment selection, delivery, and content formatting at once. | Keep email content models and HTML/text renderers in `lib/email/templates`, passing `siteUrl/logoUrl` explicitly as props. Export one typed render result (`{html,text,subject}`) per message; let `convex/emailActions.ts` be only the Resend/delivery adapter. |
| MOD-10 | `components/signup/flow-rules.ts:13-18`; `convex/signupCatalog.ts:493-500,1120-1143` | HIGH | The UI decides that accommodation is configured from `config && nightBefore !== null`. `nightBefore` is a display-rate projection, not the server's eligibility signal; it can be null when a display rate is incomplete even while the shared server context still has configured accommodation. The UI can then skip the occupancy step and submit no preferences, while `submitSignupEnvelope` requires one validated preference per attendee for configured accommodation. | Add an explicit server-derived `optionsOnlyEligible`/`hasConfiguredAccommodation` field to the public catalog contract and use it in the flow rules. Treat `nightBefore` as optional display data only; never infer business eligibility from a copy/rates sub-object. |
