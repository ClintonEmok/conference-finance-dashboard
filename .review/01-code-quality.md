# v6.0 Production-Readiness Review — Code Quality & Correctness

The review found several production-blocking correctness and fail-closed defects. The most serious issues are public Convex boundaries that fail open when configuration is missing, idempotency paths that can create duplicate orders or return non-stored results, and preview seed/backfill logic that can write the wrong or incomplete data. Typechecking passed, but that does not exercise these transactional and deployment-state edge cases.

| ID | File:line | Severity | Description | Why it matters | Suggested fix |
|---|---|---|---|---|---|
| CQ-01 | `convex/signupSubmission.ts:423-455` | CRITICAL | The public signup mutation accepts submissions without a token whenever `SIGNUP_SUBMISSION_SECRET` is absent on the Convex deployment. | Anyone can invoke the generated Convex mutation directly and bypass both Turnstile and the Next.js rate limiter. A missing production secret therefore disables the security boundary rather than failing closed. | Make the secret mandatory for the public mutation and reject when it is absent. If legacy no-token operation is required, expose it only through a deliberately private migration path, not the public mutation. |
| CQ-02 | `convex/emailActions.ts:227-231,260-325,327-332` | CRITICAL | `sendSignupConfirmationTest`, `sendAnnouncementTest`, and `resendOrderConfirmation` are public actions with no identity or operator authorization check. The first two accept an arbitrary recipient and arbitrary links/content. | Any caller with the Convex URL can send real mail through Resend, spam arbitrary recipients, and incur provider cost. The resend action also lets callers trigger mail to any order whose ID they obtain. | Make test/resend actions internal, or require and verify an authenticated operator identity/role inside each action before calling Resend. Do not rely on the dashboard UI for authorization. |
| CQ-03 | `convex/backfillLegacyAccommodationPreferences.ts:69-93`; `convex/seedPreviewSimulation.ts:175-196` | CRITICAL | The preview guard skips deployment validation when `CONVEX_SITE_URL` is unset, and when it is set the allowed deployment is partly caller-controlled and compared using permissive `endsWith` checks. | `preview: true` is caller-supplied, so a production deployment with missing guard configuration can execute destructive writes. Suffix matching can also accept unrelated values such as a domain suffix collision. | Fail closed if the deployment identity or fixed preview allowlist is unavailable. Read the expected deployment only from trusted environment configuration, require exact normalized equality, and reject caller-supplied override values. |
| CQ-04 | `convex/signupSubmission.ts:494-509,991-1008` | CRITICAL | An unexpired idempotency record with the same `(eventId, idempotencyKey)` but a different digest is not treated as a conflict. The code falls through and inserts another order and another idempotency row. | Reusing a key with a changed payload can create duplicate bookings, defeating the idempotency contract and making retries non-deterministic. The schema index is not unique, so nothing prevents the duplicate rows. | After loading the key records, explicitly reject any unexpired matching-key record whose fingerprint differs. Enforce one active record per event/key or make the mutation atomically claim the key before creating the order. |
| CQ-05 | `convex/signupSubmission.ts:467-524`; `convex/signupSubmission.ts:238-270` | HIGH | Signup replay does not return a persisted response. It stores only `orderId` and reconstructs `restorePayload` from mutable child rows; those reads are also capped at 500 rows. | A replay after an admin change can return a different payload from the original response, and a large order can replay truncated attendees/options. This violates stored-response idempotency and can cause the client to restore incomplete state. | Persist the complete canonical response (or an immutable response document) with the idempotency record and return it verbatim. If reconstruction is retained for migration data, detect truncation/corruption and fail rather than returning partial data. |
| CQ-06 | `convex/publicTracking.ts:614-629,632-645,687-721` | HIGH | `getTrackPaymentEditContext` reads option child rows with `.take(500)` while selection rows are loaded without the same complete-set guarantee. | For an order with more than 500 option rows, the UI receives an incomplete current selection. Saving that context sends a replacement missing the omitted rows, and `updateAccommodation` then deletes those rows, causing silent data loss. | Load all child rows through a complete bounded/paginated strategy, or reject an over-limit order before exposing an editable context. The read model must never produce a replacement set from a truncated child set. |
| CQ-07 | `convex/publicTracking.ts:868-895,1191-1200` | HIGH | The unchanged-edit branch writes no audit/idempotency record, so the accepted request is not replayable as a stored response. | A retry with the same key can return `unchanged` again with newly posted payment totals, or behave differently after another edit. This contradicts the documented CR-03/CR-08 exact replay behavior. | Persist a no-op idempotency/audit row containing the complete canonical result and request digest, or use a separate idempotency table. Return `replayed` from that stored row on subsequent identical requests. |
| CQ-08 | `convex/publicTracking.ts:1166-1200,1208-1236` | HIGH | The before/after selection digest omits server-owned `nightCount` and stay timestamps. If the event configuration changes but buyer choices do not, the request is classified as unchanged and the row is not refreshed. | The no-op result is then calculated from the old persisted night count, despite the UI promising current configuration pricing. This can under- or over-charge after a base-night/configuration change. | Include all server-derived persisted pricing inputs in the no-op comparison, or always refresh the resolved stay fields before returning an unchanged result and then calculate from the refreshed rows. |
| CQ-09 | `lib/domain/finance/accommodation-amounts.ts:331-357`; `convex/finance.ts:205-214` | HIGH | Every selected option is hardcoded as `unit: "per_night"`; the canonical finance context drops the option definition's `unit`, even though the schema permits `per_person`. | A valid custom per-person option is charged as price × quantity × nights instead of price × quantity. The canonical amount due, receipt lines, snapshots, and edit results are wrong. | Carry `unit` through the resolved option/context types from `accommodationOptions` and apply the `per_person` branch in both live pricing and snapshot construction. |
| CQ-10 | `convex/backfillLegacyAccommodationPreferences.ts:116-168,221-235` | HIGH | The backfill reads only the first 500 attendees/tickets/selections per order, then treats the truncated set as complete and marks the order resolved. It also silently chooses the last ticket row when an attendee has duplicate ticket rows. | An order over the cap can receive only a partial preference set and be skipped forever on the next idempotent run. Malformed duplicate-ticket orders are not rejected fail-closed, so the generated preference may not represent the order's actual entitlement. | Iterate the complete order set or explicitly detect `cap + 1` and classify the whole order unresolved. Validate exact attendee/ticket cardinality and reject duplicate or cross-event ticket references before inserting anything. Process orders in scheduled transaction-sized batches. |
| CQ-11 | `convex/seedPreviewSimulation.ts:173-201,274-285` | HIGH | The optional `slug` argument is used only for the final lookup/response; the inserted snapshot is always the fixed `LEGACY_EVENT_SLUG` fixture. | Calling the mutation with another slug appears to target that event but still writes the legacy simulation event and related rows. This violates the stated event-scope safety guarantee and can surprise an operator. | Reject any slug other than the fixture slug, or parameterize the snapshot and all stable references from the requested event. Do not accept an argument that is ignored by the write path. |
| CQ-12 | `convex/seedPreviewSimulation.ts:207-269`; `convex/seedPreviewSimulation.ts:42-121` | HIGH | Seed idempotency scans only the first 2,000 documents in each table and relies on stable keys that are not consistently parent/event scoped (for example attendee keys, labels, and slot labels). | Existing rows beyond the cap can be duplicated on rerun. An unrelated row with the same unscoped key can be treated as a seeded row and receive logical-ID mappings, causing children to attach to the wrong order/event. | Use event/parent-qualified stable keys and indexed, scope-specific lookups. If a complete scan is required, paginate it; otherwise fail closed when the cap is reached instead of claiming idempotency. |
| CQ-13 | `convex/finance.ts:255-276,398-402` | HIGH | Missing ticket-type documents are omitted from `ticketTypePriceById`, and `deriveOrderAmountBreakdown` consequently prices those ticket selections at zero. | A dangling or deleted ticket reference silently lowers the canonical amount due and can present a booking as cheaper/paid when its ticket charge is unknown. This is not fail-closed money handling. | Treat any referenced-but-missing ticket as a corrupt order and throw/mark the projection invalid. Do not silently substitute a zero price for a required ticket line. |
| CQ-14 | `convex/signupSubmission.ts:459-463`; `convex/publicTracking.ts:306-319` | MEDIUM | Signup persistence trims the booker email but does not lowercase it, while email lookup lowercases the search input before querying the exact-case index. | A booking submitted as `Booker@Example.com` cannot be found through the email search using the normal lowercase address, even though ownership checks elsewhere treat email case-insensitively. | Normalize booker email with one shared lowercase normalizer before storing/indexing, or provide a canonical lookup path that does not depend on case-sensitive stored data. |
| CQ-15 | `app/api/track-payment/[bookingRef]/route.ts:249-269`; `lib/domain/signup/submission.ts:277-294` | MEDIUM | Positive fractional `quantity`/`nights` values pass validation and are then floored; e.g. `0.5` becomes zero. The resolver accepts zero for ordinary options. | The route can persist an option selection with zero quantity/nights, producing a malformed selection and inconsistent behavior between input validation, digesting, and money/receipt semantics. | Require `Number.isInteger(value)` in both HTTP and server normalization, and reject non-positive integers before flooring. Repeat the invariant in the shared resolver/Convex mutation. |
| CQ-16 | `convex/emailActions.ts:121-139,191-215` | MEDIUM | `sendOrderConfirmationResendEmail` calls `sendSignupConfirmationEmail`, which logs a `signup_confirmation`, and then logs a second `order_confirmation_resend` for the same send. | Sent-email audit data contains two records for one message, making delivery history and operational counts incorrect. | Separate rendering/sending from logging, and let the resend path write exactly one resend-specific audit record. |
| CQ-17 | `convex/signupSubmission.ts:1036-1059`; `convex/emailActions.ts:77-145` | MEDIUM | Signup confirmation delivery errors are caught and reduced to a logged/returned failure after the booking transaction has committed; the scheduled caller does not inspect the action result or schedule a retry. | A valid booking can permanently lose its confirmation email with no durable retry or operator-visible failure record, while the user sees a successful submission. | Record an outbox/job with retry state, or have the scheduled action throw after durable failure so Convex retry handling can run. Store the failure and expose it to operators. |
| CQ-18 | `convex/signupSubmission.ts:153-181` | MEDIUM | `buildBookingRef` derives the public booking reference from a signed 32-bit non-cryptographic hash and assumes the resulting value is unique. | Different event/key/time inputs can collide, causing `first()` booking lookups to resolve the wrong order or making a reference ambiguous. The public tracking/edit surfaces depend on this value as a locator. | Generate a collision-resistant random/reference ID, or use a full cryptographic digest with a uniqueness check/retry before committing the order. Do not rely on a 32-bit hash as an identifier. |
