# DRY / Duplication Review — v6.0 Production Readiness

## Summary

The change set contains several genuine duplicate contracts, especially around
security gates, public URLs, database row loading, catalog projections, and the
two buyer accommodation editors. These are not merely stylistic repeats: the
duplicated code can drift and make different public surfaces enforce or display
different behavior. The HMAC envelope schemas and token lifetimes are
intentionally different and should remain separate; only their low-level crypto
primitives should be shared.

## Verified acceptable local duplication

- `canonicalizeSignupEnvelope` and `canonicalizeEditEnvelope` have different schemas, normalization rules, and security bindings. Combining them into one “generic envelope” would make the signed domains less obvious and risks cross-surface replay mistakes; only the crypto primitives in DRY-01 should be shared.
- The long-lived ownership edit token, short-lived route request signature, and signup submission token intentionally have different message domains and expiry behavior. Their mint/verify entry points should remain separate after extracting the low-level HMAC helpers.
- React-email and browser Tikkie components are separate rendering platforms. Their payment CTA behavior should not be merged into one component; only the email inline style base in DRY-04 is a valid extraction.
