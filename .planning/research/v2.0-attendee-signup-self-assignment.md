# Research: v2.0 Attendee Signup + Accommodation Self-Assignment

**Date:** 2026-03-29
**Scope:** Full milestone research refresh for non-admin signup and family room self-assignment.

## 1) Goal and User Outcome

Primary outcome is a guided public flow that captures room-allocation-critical data at signup time, so families/groups self-assign early and operators perform less cleanup later.

Confirmed journey:

1. Ticket selection
2. Room assignment (only when accommodation applies)
3. Attendee details + notes
4. Review + submit

## 2) Current System Baseline

From codebase inspection and prior phases:

- Existing accommodation and allocation logic is centered on `ticketTailorAttendees` and `assignedRoomId`.
- Accommodation occupancy is already single-sourced from attendee assignment state (no mutable occupancy counters).
- Existing dashboard/operator flows are Clerk-protected; public route space is open because only `/dashboard(.*)` is gated in `proxy.ts`.
- Existing event/order flows are integration-first (Ticket Tailor), with strong finance reconciliation behavior that must remain stable.

Implication: v2.0 should be additive and source-compatible, not a disruptive replacement.

## 3) Technical Constraints (Convex + Existing Patterns)

From `convex/_generated/ai/guidelines.md` and Convex docs refresh:

- Keep related writes in one mutation when consistency matters (atomic submission envelope).
- Use validators for all public function args and returns.
- Keep queries bounded/indexed; avoid unbounded full scans.
- Design mutations to be deterministic and safe under retry semantics.
- Put capacity/duplicate guards in mutation boundary (same transaction as write).

## 4) Critical Risks and Required Mitigations

1. **Partial signup writes**
   - Risk: booker, attendees, assignments, and notes diverge.
   - Mitigation: one atomic mutation for full submission envelope.

2. **Room assignment drift across source types**
   - Risk: internal/public signup records cannot feed existing accommodation views.
   - Mitigation: canonical attendee-room assignment contract that operator reads can consume directly.

3. **Public route abuse/spam**
   - Risk: unauthenticated signup endpoint abuse.
   - Mitigation: route + mutation rate limiting, honeypot, and idempotency key strategy.

4. **Duplicate/capacity race conditions**
   - Risk: overbooking or duplicate registrations during concurrent submits.
   - Mitigation: transactional guards at write boundary.

5. **Backward compatibility regressions**
   - Risk: TT/Tikkie dashboards break while adding internal/public path.
   - Mitigation: source-agnostic read contracts and phased adapter rollout with verification.

## 5) Recommended Architecture Direction

- Introduce a canonical signup submission contract independent of page composition.
- Keep event source explicit (`integration` vs `internal`) but expose one public-facing read shape.
- Keep operator handoff explicit: submission data should be consumable without post-processing transforms.
- Continue incremental rollout by phase:
  - **Phase 18:** domain contracts + atomic writes + transactional/public safety guards
  - **Phase 19:** non-admin multi-step UX implementation
  - **Phase 20:** operator read integration + compatibility verification

## 6) Requirement Impacts

Research confirms and strengthens these requirements:

- Multi-step ticket-first flow with conditional accommodation step
- Booker-managed assignment and explicit unfilled-bed warning
- Mandatory rooming details fields per attendee
- Atomic submission + transactional duplicate/capacity checks
- Operator handoff and source compatibility
- Public abuse protections (rate limits/honeypot/idempotency)

## 7) Milestone Readiness Verdict

**Ready to proceed** with planning and execution.

No blocking unknowns were found. Main challenge is careful contract design to bridge new public/internal signup data into existing accommodation and finance surfaces without regressions.
